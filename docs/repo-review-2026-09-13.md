# Repo 重新審查：需求回顧與調整順序

審查日期：2026-09-13。檢查版本：`2026.08.30.6`；HEAD：`fc52049dd69de7afe844ec5f05a61c0943a78359`，包含工作區既有未提交修改。

本次是審查，不是修正或臨床驗證。只新增本報告，未修改產品程式、測試、設定或 `.env.local`，未呼叫真實 Gemini API，未提交 Git。以下「建議／省略化療」等文字是程式實際輸出或測試情境，不是對病人的醫療建議。

## 結論

目前已有「先填個案 → 定位來源 → AI 摘要 → 選療程查健保」的雛形，但仍不能把「測試全綠」解讀成跨癌別、跨病程的判讀已可靠。

最需要先修的是輸入語意、病程路由和來源驗證。兩個上一輪精準化的頁碼分流與實際 PDF 不符；Gemini 則仍是術後化療專用的輸出契約，不能直接當成所有癌別／病程的摘要引擎。這些問題應先修，再擴充癌別或繼續縮短畫面。

## 優先修正：可能改變判讀或造成錯誤來源背書

### R01 [P1]「不適合接受化療」被判成適合

- 位置：`clinical-matcher.js:747`。
- 原因：`/適合接受化療/.test(chemotherapyCandidate)` 同時命中「適合接受化療」和「不適合接受化療」。
- 重現：完整乳癌術後欄位，化療適用性選「不適合接受化療」，Oncotype DX RS 30。
- 實際：`status: ready`、`level: recommended`，輸出 RS ≥26 的化療方向，沒有缺漏警示。
- 調整：改用標準化選項的精確比對。所有否定、待確認與未填值都應各自測試，不能用肯定字串包含判斷。

### R02 [P1] 非 Oncotype／未取得數值，仍被分流為低 RS

- 位置：`clinical-matcher.js:766`、`:770–787`。
- 重現：停經後 HR+/HER2- 術後案例，基因表現檢測選「其他基因表現檢測」或「不適用」，RS 留白。
- 實際：沒有要求有效分數，輸出「Recurrence Score <26：以術後內分泌治療為主」，`status: ready`。
- 原因：只有 assay 明確等於 Oncotype DX 時才檢查有限數值；其他 assay 的 `NaN >= 26` 為 false，直接落入低分分支。
- 調整：先驗證檢測種類、有效結果與適用情境，才允許進入數值門檻。換檢測種類時要排除舊分數殘留。

### R03 [P1] 過去做過手術，會蓋過目前的轉移／第一線病程

- 位置：`clinical-matcher.js:612–615`；同型啟用條件見 `:1068–1071`、`:1263–1268`、`:1447–1449`。UI 影響位置：`index.html:2345–2355`。
- 重現：乳癌欄位改為「轉移／全身性」「第一線」，保留歷史「先手術」與原病理欄位。
- 實際：術後評估仍 `active: true`，產生術後 RS 分支。UI 隨後可按術後來源白名單過濾候選，Gemini 也接收錯置的規則摘要。
- 調整：目前病程／本次治療目的優先，歷史手術不能直接啟動術後流程。互相矛盾的欄位應要求確認，而不是自行選一路徑。

### R04 [P1] NSCLC IB／IIA 被導向腳註頁，而非主決策頁

- 位置：`clinical-matcher.js:1237–1238`。
- 程式：IB／IIA 選 `NSCL-4A`，其他分期選 `NSCL-4`。
- 原 PDF 核對：本機 NSCLC v6.2026，PDF p.29 `NSCL-4` 是包含多個手術病理分期的主流程；p.30 `NSCL-4A` 是 NSCL-4 的腳註，不是 IB／IIA 專用主流程。
- 測試盲點：`tests/clinical-matcher.test.cjs:541–580` 的假資料把兩頁自行命名為不同分期流程，測試遂鞏固了錯誤假設。
- 調整：主頁與腳註保持正確關係；依頁面實際內容及文件版本核對，不能只依代碼猜測分期。

### R05 [P1] 直腸癌手術後追蹤，被連到非手術追蹤頁

- 位置：`clinical-matcher.js:1632–1643`。
- 原 PDF 核對：本機 Rectal Cancer v2.2026，PDF p.21 `REC-10` 是手術治療後追蹤，包含經腹切除／經肛門局部切除；p.22 `REC-10A` 是非手術管理後追蹤。
- 實際：完成 TNT 後手術、部分手術後 observation／局部切除情境仍把 `REC-10A` 加為 supporting page。
- 測試盲點：`tests/clinical-matcher.test.cjs:604–638` 沒有提供 REC-10，且直接預期術後使用 REC-10A。
- 調整：明確區分 operative 與 nonoperative 的追蹤路由；測試需同時提供兩頁，驗證選對及排除錯頁。

### R06 [P1] 無 PDF／缺附錄時，NSCLC 評估可直接崩潰

- 位置：`clinical-matcher.js:987–988`、`:1197`、`:1217–1218`。
- 重現：NSCLC IB、pT2a pN0、R0、無高風險特徵、EGFR exon 19 deletion，文件陣列為空。
- 實際：`TypeError: Cannot read properties of null (reading 'option')`。
- 原因：找不到來源時 `regimenEntry` 回傳 null，仍加入 targeted；`.some(item => item.option?.needsReview)` 沒有防護 item 本身。
- 調整：來源缺失必須回傳可呈現的待核對狀態；不能因缺資料拋出例外，也不能把不存在的來源當已核對。

### R07 [P1] 完成化療後，後續免疫治療評估一起消失

- 位置：`clinical-matcher.js:1169`、`:1210–1214`。
- 重現：NSCLC IIB、pT3 pN0、4.2 cm、R0、腺癌、cisplatin 適用、PD-L1 80、無已知可標靶變異，使用含化療與其他術後治療的測試頁。
- 實際：尚未記錄完成化療時列出化療及 atezolizumab／pembrolizumab 候選；新增術後 Cisplatin/Pemetrexed 已完成 4/4 的歷程後，療程清單變空。
- 原因：`chemoEligible` 同時代表「現在還要化療」和後續免疫治療的入口；完成化療使兩者一併關閉。
- 調整：拆開「是否尚需化療」「是否已完成前置治療」「接下來要評估什麼」。此處指出的是評估候選漏失，不等於本報告判定病人應接受某藥。

### R08 [P1] 原頁沒有擷取到療程，程式仍能製造帶來源的療程項目

- 位置：`clinical-matcher.js:987–995`。
- 重現：結腸癌 Stage IIIB、pT3 pN1、pMMR、R0；提供 COL-4 p.13，但 `options: []`。
- 實際：仍產生 CAPEOX 3 個月、FOLFOX 3–6 個月，連結該來源頁，沒有強制 `needsReview`。
- 原因：找不到符合 pattern 的原始 option 時，以程式內建 label 建立新的 option。
- 調整：區分「規則內建的候選名稱」與「原頁實際擷取且符合條件的療程」。解析缺漏或版本不符時，不得讓頁碼產生已被該頁證實的錯覺。

### R09 [P1] Gemini 所有癌別／病程都被要求先回答術後化療

- 位置：`gemini-summary.cjs:5–9`、`:98–105`；通用入口：`index.html:2554`。
- 實際：固定四種 decision 中，三種是輔助性化療方向，另一種是證據不足；prompt 固定要求先判斷「術後輔助性化療」。
- 重現：給 `buildPrompt` 一個轉移性 NSCLC 第一線案例，任務指令仍是術後輔助性化療。
- 調整：先確認本次臨床問題與病程，再選摘要契約。不可把術後化療專用 prompt 套到轉移性、術前、維持、追蹤及其他治療問題。

### R10 [P1] AI 沒有有效證據，也能保留肯定結論；送入的來源過度截斷

- 位置：`gemini-summary.cjs:136–151`；`index.html:2509–2543`。
- 重現：呼叫 `normalizeSummary`，提供肯定化療結論、不存在的 evidence ref，輸入 evidence 為空。
- 實際：不存在的 ref 被刪除，但肯定的 decision／headline 原樣保留，uncertainties 可以為空。
- 來源問題：前端只送每頁前 8 個 option 的 label，最多 12 頁；沒有保留該 option 的條件、群組或完整來源文字／腳註脈絡，也未傳入完整治療歷程及 decision caveats。
- 調整：關鍵結論需綁定可驗證的引用與適用條件；沒有證據或來源衝突時不能維持已證實式結論。優先送命中分支的片段與腳註，而非單純截取前幾個藥名。引用識別也應包含文件／版本，不只章節與頁數。
- 限制：這是本機輸入／輸出契約測試，沒有聲稱本次真實 Gemini 曾產生上述錯誤答案。

## 第二批：需求落差、顯示一致性與部署防護

### R11 [P2] 原案例仍有雙重答案，精準化只限少數特判

- 位置：`clinical-matcher.js:766–769`、`:945–950`；`index.html:2491–2507`。
- 原 ER-low、PR 陰性、停經後 pT2 pN1、Grade 3、Ki-67 35%、LVI 有、3 cm、未評估基因表現的案例，規則仍輸出「需先完成基因表現結果判讀」。
- BINV-6／特定 BINV-M 的精簡僅在上述狹窄型態啟用；改為 pT1c 或一般 HR+ 情境，主頁又回到較廣的 BINV-4／6／7／8 集合。
- 調整：先建立分支適用性與衝突介面，再把 AI 整理整合進共用結果。不能把「讓 AI 同意化療」當成規則或來源已修正。

### R12 [P2] 專屬療程清單為空時，健保選單恢復未篩選清單

- 位置：`index.html:2386–2398`。
- 原因：只有 `adjuvant.active && adjuvantNccnMatches.length` 時才採用專屬療程；否則退回原始 `nccnMatches`。
- 重現：對此 UI 表達式提供 active 的術後評估、空 regimens 及非空原始候選，結果採用原始候選。
- 影響：完成療程、observation 或缺少對應來源時，原先隱藏的藥物／療程可能重新進入健保選單。
- 調整：區分「沒有專屬評估」與「專屬評估明確沒有候選」。來源頁、AI、療程與健保應消費同一份已判讀結果。

### R13 [P2] 直腸癌路徑的全形字元／否定字串處理不一致

- 位置：`clinical-matcher.js:123`、`:1455`、`:1638`、`:1650`。
- 重現：使用表單合法選項「免疫治療後完全臨床反應／未手術」。輸入經 NFKC 正規化，斜線變成 `/`，但 nonoperative 的 regex 仍使用 `／`。
- 實際：nonoperative 不成立，繼續要求病理分期、pT／pN、切緣／CRM 等術後資料。
- 另見：`/完成 TNT/` 也能命中「未完成 TNT」；來源選頁與 branchLabel 使用此判斷。
- 調整：用穩定的路徑 ID，不以顯示中文字串判斷狀態；把標點、否定、待確認納入反例測試。

### R14 [P2] 首頁「大腸直腸癌」捷徑沒有接上專屬結腸／直腸評估

- 位置：`index.html:1957`；`clinical-matcher.js:1670–1673`。
- 實際：捷徑進入 `colorectal_cancer`；dispatcher 只辨識 `colon_cancer` 和 `rectal_cancer`。以 umbrella ID 呼叫會回 inactive，通用表單也不是兩者完整的術後表單。
- 調整：捷徑先選原發部位，或明確路由至兩個專屬癌別，避免最常用入口繞過已完成的功能。

### R15 [P2] 搜尋結果被首頁品質資訊推到畫面下方

- 位置：`index.html:2006–2028`、`:2072–2082`。
- UI 實測：隔離的全新本機 origin，輸入「乳癌」，可存取樹出現「找到 1 個結果／乳癌」，截圖仍只看到搜尋框與 NCCN 指引品質總覽。
- 原因：缺指引明細預設展開；search-results 位在整段品質資訊後；搜尋只隱藏 home-content，不隱藏前面的品質卡。
- 調整：搜尋結果緊接輸入框；品質資訊縮成次要入口，搜尋時收起。個案表單也應先問病程與治療目的，再按需展開欄位，避免一次呈現全部 29 個欄位。

### R16 [P2] 本機付費 AI 端點缺少來源與請求格式防護

- 位置：`server.cjs:46–58`、`:116–121`。
- 本機模擬：不載入真實 key、stub 掉 AI 呼叫後，送入 `Origin: https://unrelated.example`、`Content-Type: text/plain` 的有效 JSON POST；回應 200，summarizer 被呼叫一次。
- 影響：到達此端點的非預期來源請求可能觸發付費 API；不能只依賴 loopback 綁定或未設定 CORS 回應。
- 調整：驗證允許的 Host／Origin、JSON Content-Type，加入本機請求驗證及必要限流／逾時。瀏覽器私有網路限制的行為不同，本測試不等於宣稱所有瀏覽器都可被遠端網站直接利用。

### R17 [P2] 隱私說明仍宣稱「不上傳資料到雲端」

- 位置：`README.md:204`、`index.html:5026`；實際傳送：`gemini-summary.cjs:155–196`。
- 實際：按 Gemini 後，本機伺服器會將結構化欄位、規則摘要與擷取文字送往 Google；雖然不送完整 PDF，仍不是完全不上雲。
- 調整：區分「預設本機處理」與「使用者啟用 Gemini 時的資料外送」，列出目的地、內容和取消方法；不能把 `store: false` 當成已證實供應商完全不保留資料。

1. **先修判讀入口與資料語意。** R01、R02、R03、R06、R07、R13；建立已知／未知／不適用／衝突狀態，避免字串與空值暗中做醫療判斷。
2. **修正來源與證據鏈。** R04、R05、R08、R10；每份已支援指引綁定版本，建立「案例條件 → 正確流程／腳註 → 適用候選」的人工核對基準。
3. **讓規則、AI 與 UI 使用同一份結果。** R09、R11、R12；區分主要方向、選項、缺漏、來源、不確定性。沒有來源時保留問題整理能力，但不產生貌似已證實的療程。
4. **修正入口與資訊層次。** R14、R15；首屏聚焦病程、關鍵條件與當下行動，來源、完整候選、健保與品質稽核逐層展開。
5. **補安全／隱私說明，再按癌別擴充。** R16、R17；其他癌別沒有通過分支驗收時，清楚標示「僅提供來源候選」，不要展示成已完成精準判讀。

共同驗收矩陣應至少包括：分期、亞型／生物標記、目前治療階段、已完成／未完成療程、禁忌或不適用、未填／待檢、矛盾資料、沒有 PDF、缺頁／擷取失敗、版本改變。每個案例同時測「應出現什麼」和「不應出現什麼」，並涵蓋規則摘要、原頁、AI payload、療程及健保選單。

能批次改的是這些共通機制；各癌別的臨床分支仍需原始來源核對與代表案例驗收，不宜用一個 AI prompt 或單一頁碼白名單取代。
